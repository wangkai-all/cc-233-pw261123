# 双通道采集与完整性证据台

同一份业务数据同时通过两条**互相独立**的通道进入本地采集面：

| 通道 | 特点 | 风险 |
| --- | --- | --- |
| 业务推送（push） | 及时，按事件顺序投递 | 可能整段丢失，且尾部丢失时"没有消息"看起来和"没有新数据"一样 |
| 分页拉取（pull） | 完整，keyset 分页 | 有复制延迟，只能看到快照；成本按页计 |

两条通道之间没有共享序号，只能靠 **业务键 + 修订号 + 内容摘要** 交叉核对。本页面把"数据是否正确"和"完整性是否被证明"拆成两个独立问题：前者靠幂等归并，后者靠可复算的扫描证书。全部数据为本地虚构。

## 运行

```bash
# 启动（默认 127.0.0.1:8765，数据库 data/collector.db，首次启动自动建表并播种虚构数据）
python3 -m app.server --port 8765
# 或：HOST=0.0.0.0 PORT=8765 DB_PATH=/tmp/x.db python3 -m app.server

# 测试
python3 -m unittest discover -s tests -v
```

只依赖 Python 3.10+ 标准库（`sqlite3` / `http.server` / `threading`），前端为无构建步骤的原生 JS。浏览器打开 <http://127.0.0.1:8765>。

## 结构

```
app/db.py          SQLite 模式与线程安全的 Store（WAL，单连接 + RLock，显式事务）
app/sources.py     虚构上游：追加式修订日志 + 两条独立通道（可见性延迟、丢失、停机注入）
app/collector.py   归并规则、可续跑全量扫描、定向补采、冲突裁决、策略规划、状态/证据
app/scenarios.py   两个独立本地源（orders / inventory）与六种演示场景
app/server.py      HTTP 路由、后台 worker 注册与停止
app/static/        三个页签：采集与核对 / 逐条归属 / 证据与请求账本
tests/             39 个用例：修订顺序、幂等、缺失非删除、冲突、缺口、扫描证书、补采、结论
```

## 六条硬规则（均有测试）

1. **身份是 `(source_id, biz_key)`，到达顺序不参与任何判断。** 同一键的两个事件乱序到达，结果只由修订号决定。
2. **只有严格更高的修订能替换本地状态。** 修订相同 + 内容摘要相同 = 重复投递，计数后丢弃；修订相同 + 内容不同 = **冲突**，写入 `conflicts` 表并进入人工裁决队列，绝不按先后覆盖。低修订永远被忽略（`stale`）。
3. **重复识别键是 `(biz_key, revision, content_hash)`。** 同一条记录先经推送、再经拉取到达，只入库一次并计入 `duplicate`；同一页重放两次结果不变。
4. **查不到不是删除。** 分页里没有某键、点查返回 `not_found`，都只保留本地记录并登记疑点。只有"更高修订的墓碑"才会删除。
5. **一页即一个事务。** 页面数据、续跑游标、请求账本在同一 SQLite 事务中提交；工作进程随后崩溃，要么整页已生效并记账，要么完全没发生——续跑不会重复入库。
6. **证书只由完整的全量扫描产生。** 必须终止于空页、keyset 游标链连续，并通过逐页哈希链校验。

## 完整性证据是怎么造出来的

一次全量扫描开始时先确定 **快照 cutoff** 和 **覆盖水位 `coverage_seq`**：cutoff 时刻对拉取可见的最高"接受写序号"。之后按业务键 keyset 分页读取，每页记录：

```
page_hash = H(prev_page_hash | row_digest | covered_to | exhausted)
```

同时把扫描 id、页序号、覆盖区间、行数、成本写进 `requests` 账本。扫描结束（空页）后证书（`scan_id`、`coverage_seq`、`chain_head`、页数）落在 `source_state`。

展示结论前会用 `requests` 账本**现场重算**整条链：

- 任何一页被篡改、删除或补写 → `verified_now=false`，结论直接降为"未证明"；
- 证书不存在或未完整 → `not_proven`；
- 证书有效但仍有未排除缺口/疑点/冲突，或快照之后的尾部未被连续推送覆盖 → `open_items`；
- 证书有效、无未决项、且 **推送游标已越过推送头部**（说明快照之后的写入全部连续到达、没有未知尾部）→ `proven`。

关键点：`proven` 从不表示"推送没有丢"，它表示"有一个快照前全覆盖的可复算证书，且快照后的每一批推送都连续到达"。快照水位与推送头部的差值会原样显示，不做四舍五入的乐观推断。

## 全量核对 vs 定向补采

页面右侧的"策略选择"同时给出两种选项的**请求成本**与**可证明边界**，以及推荐项和仍未排除项：

| | 全量核对 | 定向补采 |
| --- | --- | --- |
| 成本 | `ceil(已知键数 / 页大小) + 1` 页（对未知键只会更多，故为下限） | 每个具名键 2 次点查（取回 + 二次读取确认稳定） |
| 能证明 | 快照时点所有业务键的最新版本，包括采集端从未听说过的键 | 仅清单中的键；且要求两次读取间修订未变化 |
| 不能证明 | 快照水位之后的写入、拉取延迟窗口内的变更 | 清单之外的未知遗漏；也不能扩大证书覆盖范围 |
| 何时推荐 | 有推送缺口、有未裁决冲突、或尚无可用证书 | 只有具名疑点（冲突已裁决）时 |

定向补采把记录修对了，但**不会**让结论变成 `proven`——它没有覆盖证据。这一点在 `Conclusion` 测试与演示流程中都被固定下来。

## 故障与恢复

- **推送断档**：消费端发现下一批序号大于游标 → 在推送序号和写序号两个空间同时登记缺口，并从上游日志还原缺口涉及的 `(业务键, 修订)` 清单，逐个进入疑点队列。
- **尾部停滞**：`push_head` 由"已存储的最大事件序号"和"下一个待分配推送序号"共同决定，因此上游接受了写入但事件全部丢失时，游标追不上头部，尾部会被识别为 `push_tail_not_delivered`。
- **半途停止**：全量扫描与定向补采都是可续跑 run。可以模拟崩溃（全量按页、补采按键）或主动停止；run 留下 `interrupted`/`stopped` 状态和游标，点"继续"从断点续跑，已提交的页/键不会重放。
- **补采期间又被修订**：取回后立刻再读一次；若修订变化，应用更高修订并进入下一轮（最多 4 轮）。只有稳定的那次读取才写入拉取确认摘要；不稳定项保留为疑点。
- **同一记录双路到达**：见规则 3。
- **裁决冲突**：`keep_local` 保留本地字节；`accept_remote` 采纳冲突版本，但**不会**伪造"拉取已确认"——该记录的确认状态仍为未确认。

## 页面演示路径

1. 左侧选中 `orders`，点"接收推送"。右栏显示统计、结论与证据行。
2. 点"执行全量核对" → 证书生成，结论 `proven`；证据面板中可见页哈希与请求账本。
3. 场景 "推送断档" → 再点"接收推送"：出现序号跳变、缺口清单与疑点，结论降级，策略改推荐全量。
4. 先"执行定向补采"：记录被修对（真值核对为空），但结论仍非 `proven`；再"执行全量核对"→ 证书覆盖缺口区间，结论回到 `proven`。
5. 场景 "同修订冲突" → "接收推送"：冲突队列出现两条内容，必须选择"保留本地/采纳冲突版本"。
6. 场景 "高版本迟到"：勾选"定向补采时让上游在确认前再次修订选中键"，观察补采的稳定性循环与疑点处理。
7. 勾选"全量核对执行中模拟工作进程半途停止"：run 变为 `interrupted`，在证据页签点"继续"完成剩余页。
8. "逐条归属"页签可按业务键过滤并勾选多行，直接对选中键补采；点行看两路事件、冲突、裁决与恢复轨迹。
9. 证据页签的"演示真值核对"直接比较本地与虚构上游，**仅用于验证实现，不参与任何结论**。

## 已知边界

- `truth_diff` 是演示用 oracle，采集器本身不读取上游真值来做判断。
- 全量扫描成本以已知键数估算，是下限；页大小越小、未知键越多，真实请求数越高。
- 扫描证书证明的是"快照时点"的完整性与之后推送的连续性，不是任意时刻的实时一致性；拉取延迟窗口内的写入会体现在 `coverage_seq < head_seq` 上。
